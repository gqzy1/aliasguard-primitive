# Security and scope

AliasGuard evaluates public caller declarations about individual non-sensitive catalogue objects. It does not authenticate asset identifiers, publishers, ownership, custody or real-world existence. False declarations can produce a consistently false partition. Namespaces are interpreted from the declared scope; scope is context, not permission to change protocol rules.

Consensus checks each pair independently, but models may share systematic errors or follow injected text. Separating instructions and data, strict parsing and independent comparisons mitigate this without proving universal resistance. Real successful examples do not measure general model accuracy. Deterministic contradiction witnesses are exact for the accepted relation vector, not evidence that every semantic conflict was discovered in the original prose.

Transitive SAME inference is intentional and exposed. UNKNOWN within a supported component can become inferred sameness; direct UNKNOWN is retained in the original vector. Cross-component UNKNOWN cannot pass publication. Consumers should inspect the relation vector and inference paths when direct-pair evidence is required. No external inventory or global identity uniqueness is enforced across records or deployments.

All content is public. Avoid personal identity, confidential records and regulated decisions. This is not identity verification, a fraud verdict, an ownership registry or a physical merge operation. Consumers must bind integrations to the expected contract, protocol version, finalized successful receipt, record identity and certificate hash.

Only the owner can assess and publish its immutable catalogue; no administrator exists. Per-owner quotas are not global resource protection. Failed execution is not automatically resent, appealed or replaced. Network consensus can fail; retain any returned hash and reconcile it before another action.
